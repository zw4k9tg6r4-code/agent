# 项目分析

## 背景

Grok Build 已公开其终端编程 Agent 的运行框架和 TUI 源码。公开内容覆盖 Agent 循环、上下文组装、工具调用、文件与命令执行、工作区、Skills、插件、MCP 和子 Agent 等能力。

本项目不复制 Grok 模型，不训练或蒸馏模型，也不对 Grok Build 进行改名换皮。项目参考其公开架构边界，使用 TypeScript 独立实现一个轻量、可控、模型可切换的通用 Agent Runtime。

参考资料：

- Grok Build 开源说明：https://x.ai/news/grok-build-open-source
- Grok Build 官方仓库：https://github.com/xai-org/grok-build

## 业务目标

建立一套不绑定固定业务的 Agent 基础设施，让同一个内核通过模型、提示词、Skills 和工具配置适配不同任务，降低以后开发代码 Agent、内容 Agent、客服 Agent 或内部业务 Agent 的重复成本。

第一阶段不验证某个垂直业务是否能收费，而是验证以下平台价值：

1. Agent 能否稳定完成“理解任务—调用工具—检查结果—结束任务”的闭环。
2. 能否更换模型而不改动核心执行逻辑。
3. 能否通过权限系统阻止越界和危险操作。
4. 能否通过 Skills 和工具扩展能力，而不修改 Agent Core。
5. 能否记录并复现一次任务的关键决策和执行过程。

## 服务用户

MVP 的直接使用者是项目发起者，以及能够在本地终端运行 Node.js 的个人或开发者。MVP 不承诺面向普通消费者提供无配置体验。

## 当前状态

- 工作区是空 Git 仓库。
- 当前分支为 `master`，尚无提交。
- 当前没有代码、依赖、测试或其他工作树。
- 本机为 Windows 环境。
- 已安装 Node.js `v24.18.0`、npm `11.16.0`、Git `2.55.0.windows.2`。
- PowerShell 当前禁止执行 `npm.ps1`，因此 Windows 文档和自动化命令统一使用 `npm.cmd`，不要求修改系统执行策略。

## 当前问题

通用 Agent 容易出现三个问题：

1. 范围失控：同时实现模型、TUI、MCP、多 Agent、记忆和插件市场，导致首版无法验收。
2. 安全失控：模型拥有文件和命令工具后，可能读取密钥、越界修改文件或执行破坏性命令。
3. 价值失焦：声称“什么都能做”，但缺乏可重复评测，无法判断内核是否进步。

本设计通过严格限定 MVP、权限优先和通用任务评测集解决以上问题。

# 方案设计

## 方案比较

### 方案 A：直接 Fork Grok Build

优点：

- 最快获得完整 Agent、TUI 和工具体系。
- 可以直接研究真实产品的实现细节。

缺点：

- Rust 工程规模大，Windows 源码构建仅为尽力支持。
- 带入大量当前不需要的模块和第三方许可义务。
- 架构和发布节奏受上游影响，容易形成换皮产品。

### 方案 B：参考公开架构，用 TypeScript 独立实现轻量内核

优点：

- 可以只实现当前需要的执行闭环。
- Node.js、MCP 和 Web 生态丰富，后续扩展成本低。
- 更容易理解、测试和控制安全边界。
- 可以形成独立接口、品牌和产品路线。

缺点：

- 需要重新实现基础运行时。
- 首版不会具备 Grok Build 的完整 TUI 和成熟度。

### 方案 C：参考架构，用 Rust 独立重写

优点：

- 性能、资源控制和单文件分发上限高。
- 适合长期打造底层基础设施。

缺点：

- MVP 开发和调试成本最高。
- 对当前 Windows 开发环境和快速验证不友好。

## 最终推荐

采用方案 B。TypeScript 版本优先验证 Agent Runtime 是否可靠、安全、可扩展；只有在性能、分发或隔离出现明确瓶颈后，才评估把特定模块迁移到 Rust。

## 产品定位

MVP 是一个本地优先的通用 Agent CLI：

- 不绑定固定业务。
- 不绑定固定模型供应商。
- 工具可注册和替换。
- 权限策略可配置。
- 支持交互式任务和无界面单次任务。
- 所有关键执行记录保存在本地。

MVP 提供以下命令：

```text
agent init
agent
agent run "<任务>"
agent sessions
agent resume <session-id>
agent undo <session-id>
```

命令行为：

- `agent init`：在当前工作区创建 `.agent/config.json` 和必要目录。
- `agent`：进入交互式会话。
- `agent run`：执行一次任务，完成后以明确退出码结束。
- `agent sessions`：列出本地会话的状态、时间和消耗。
- `agent resume`：从可恢复会话继续执行。
- `agent undo`：依据会话首次修改前的检查点撤销该会话的文件变更。

## MVP 范围

### 包含

- 单 Agent 执行循环。
- OpenAI-compatible 模型适配器。
- 流式文本和结构化工具调用。
- 文件读取、文件搜索、文件修改和命令执行。
- 工作区边界与三种权限模式。
- 项目级 `AGENTS.md` 加载。
- 项目级 Skills 加载。
- 本地会话事件日志。
- 会话与 Turn 分离：交互模式可以在同一会话内完成多个用户 Turn。
- 文件修改前镜像和按会话撤销能力。
- 超时、步骤数和 Token 预算限制。
- 集成测试、安全测试和 20 个任务的评测集。

### 不包含

- 全屏 TUI。
- 浏览器控制和联网搜索工具。
- 长期记忆和 RAG。
- 多 Agent 和 Git 工作树自动编排。
- 插件市场。
- 云端账户、同步和多人协作。
- 自研或蒸馏基础模型。

## 技术基线

- 语言：TypeScript，开启严格类型检查。
- 运行时：Node.js 22 或更高版本。
- 包管理：npm Workspaces。
- 网络访问：使用 Node.js 原生 `fetch` 和流式响应能力。
- 配置格式：JSON。
- 会话记录：JSON Lines。
- 测试：单元测试、集成测试、安全测试和端到端 CLI 测试。
- 支持平台：Windows、macOS、Linux；MVP 首先在 Windows 验收。

不修改用户的 PowerShell 执行策略。Windows 下统一通过 `npm.cmd` 运行 npm 命令。

## 系统架构

### 1. Contracts

定义稳定的公共接口和事件类型：

- `ModelProvider`
- `ModelRequest`
- `ModelResponseChunk`
- `ToolDefinition`
- `ToolCall`
- `ToolResult`
- `PermissionDecision`
- `SessionEvent`
- `AgentRunOptions`
- `AgentRunResult`

其他模块只能依赖 Contracts，不得直接依赖彼此的内部实现。

### 2. Agent Core

负责：

- 接收和标准化用户任务。
- 维护 Agent 状态机。
- 区分会话生命周期和单次 Turn；只有显式结束会话才写入正常终态。
- 请求模型并消费流式响应。
- 调度工具调用。
- 把工具结果反馈给模型。
- 判断完成、失败、取消或预算耗尽。
- 生成最终任务结果。

Agent Core 不直接访问文件系统、不执行命令、不读取环境变量中的 API Key。

### 3. Model Providers

第一版实现 `OpenAICompatibleProvider`，通过配置接受：

- Base URL。
- Model ID。
- API Key 环境变量名称。
- 请求超时。
- 最大重试次数。

Provider 负责协议转换、流式解析、工具调用解析和供应商错误标准化。Core 不感知具体供应商名称。

### 4. Tool Registry

每个工具必须声明：

- 唯一名称。
- 用途说明。
- JSON 输入结构。
- 风险等级。
- 执行函数。
- 输出长度上限。
- 是否支持取消。

MVP 内置工具：

- `file_read`
- `file_search`
- `file_patch`
- `shell_execute`

`file_patch` 使用明确补丁修改文件，不允许模型无提示覆盖整个未知文件。

### 5. Permission Engine

权限系统在工具真正执行之前作出决定：

- `allow`
- `ask`
- `deny`

判断依据包括：

- 当前权限模式。
- 工具风险等级。
- 规范化后的真实路径。
- 命令内容。
- 是否涉及网络、安装、凭证、Git 远程或大范围文件操作。

### 6. Context Engine

上下文由以下内容按优先级组装：

1. Agent 基础安全指令。
2. 项目根目录中的 `AGENTS.md`。
3. 当前启用的 Skills。
4. 用户当前任务和后续指令。
5. 当前会话的必要历史。
6. 相关工具结果和文件片段。

上下文超过预算时，优先压缩旧工具输出和已完成步骤；不得丢失用户目标、安全限制、已批准决策和未提交文件变更。

### 7. Runtime Interface

CLI 只负责：

- 参数解析。
- 配置初始化。
- 用户输入和输出。
- 权限确认。
- 取消信号。
- 退出码。

CLI 不包含 Agent 决策逻辑。未来的 TUI、Web UI 或编辑器扩展应复用同一个 Core。

## 数据流

一次任务按以下顺序执行：

1. CLI 接收任务并确定工作区根目录。
2. Config Loader 读取项目配置和环境变量引用。
3. Context Engine 加载 `AGENTS.md`、Skills 和必要会话历史。
4. Agent Core 请求 Model Provider。
5. Provider 返回文本片段或结构化工具请求。
6. Tool Registry 校验工具是否存在以及参数是否符合结构。
7. Permission Engine 返回 `allow`、`ask` 或 `deny`。
8. 获准的工具由 Tool Executor 执行。
9. 工具执行前写入开始事件；执行结果经过长度限制和敏感信息清理后写入会话日志。
10. 工具结果反馈给模型，Agent 循环继续。
11. 单次 Turn 完成后写入 `turn_completed`；一次性运行结束或用户退出交互会话时才写入会话终态并返回退出码。

## 本地数据

项目级数据保存在：

```text
.agent/
├─ config.json
├─ sessions/
│  └─ <session-id>.jsonl
└─ checkpoints/
   └─ <session-id>/
```

`.agent/config.json` 可以提交到 Git，但不得包含真实 API Key。`sessions` 和 `checkpoints` 默认加入 `.gitignore`。

会话日志采用追加写入，不在原记录上改写。核心事件包括：

- `session_started`
- `turn_started`
- `user_message`
- `model_request_started`
- `model_output`
- `model_response_completed`
- `tool_requested`
- `permission_decided`
- `permission_confirmed`
- `tool_execution_started`
- `tool_completed`
- `tool_failed`
- `context_compacted`
- `turn_completed`
- `turn_failed`
- `session_completed`
- `session_failed`
- `session_cancelled`

## 权限设计

### `readonly`

- 允许读取工作区文件和搜索。
- 禁止修改文件。
- 禁止执行可能产生写入的命令。

### `workspace`

- 默认模式。
- 允许读取工作区文件。
- 允许通过补丁修改工作区文件，并创建会话检查点。
- 允许已归类为低风险的本地命令。
- 安装依赖、联网、删除、Git 远程操作和无法判断的命令必须确认。

### `trusted`

- 减少普通写入和命令确认。
- 仍然禁止工作区逃逸、读取系统密钥、广泛破坏性删除和未授权代码上传。

所有路径在授权前必须：

1. 转换为绝对路径。
2. 解析 `..`。
3. 解析符号链接或 Windows Reparse Point。
4. 验证最终目标仍位于工作区。

## 敏感信息保护

- API Key 只通过配置指定的环境变量读取。
- `.env`、私钥、证书、凭证数据库和常见 Token 文件默认不进入模型上下文。
- 工具结果写入日志前执行敏感信息清理。
- 模型请求默认不包含完整仓库，只包含当前任务必要内容。
- 任何代码上传或外部网络工具在 MVP 中均不提供。

## 异常处理

- 模型临时错误最多自动重试两次，并采用退避等待。
- 鉴权错误不重试，直接指出缺失或无效的配置项。
- 工具参数无效时允许模型修正一次；再次无效则结束该工具调用。
- 工具失败以结构化结果返回，Agent 可以修正方案或明确停止。
- 单次任务默认最多执行 30 个 Agent 步骤。
- 单个命令必须配置超时并支持取消。
- 工具输出超过上限时保留开头、结尾和截断说明。
- 上下文接近上限时执行压缩，并记录 `context_compacted` 事件。
- 用户取消后停止新的工具调用，保留已完成事件和文件检查点。
- 进程中断后，只能从最后一个完整模型响应恢复；存在“工具已开始但没有成功/失败事件”时标记为未知执行状态，不自动重放该写操作。

# 指标与验收

## 用户指标

- 新环境从安装到首次成功任务不超过 10 分钟。
- 配置错误必须提供可执行的修复提示。
- 用户可以取消任务并查看已发生的修改。

## 质量指标

- 20 个通用评测任务的首次执行成功率不低于 80%。
- Core 和 Policy 的分支测试覆盖率不低于 80%。
- 所有模型请求、工具请求、权限决定和结果均可追踪。
- 同一个会话不出现无限循环或超过配置上限后继续执行。

## 安全指标

- 工作区逃逸测试 100% 被阻止。
- 破坏性命令测试 100% 被拒绝或要求确认。
- 测试日志中不得出现注入的假 API Key。
- 未经确认不得执行安装、联网、Git 推送或大范围删除。

## 成本指标

每个会话记录：

- 总运行时间。
- 模型请求次数。
- 输入和输出 Token。
- 工具调用次数。
- 供应商返回成本或基于配置的估算成本。

MVP 不设绝对成本目标，但必须能比较不同模型和策略的成本。

## MVP 验收任务

评测集至少覆盖以下类型：

1. 分析陌生目录并解释结构。
2. 搜索特定内容并汇总结论。
3. 创建普通文档。
4. 修改已有函数并运行测试。
5. 根据失败测试定位并修复简单缺陷。
6. 在命令失败后调整执行方案。
7. 在缺失 API Key 时给出明确配置提示。
8. 阻止读取工作区外文件。
9. 阻止路径穿越和链接逃逸。
10. 要求确认危险命令。
11. 取消长时间运行的命令。
12. 截断超长工具输出。
13. 压缩过长上下文。
14. 从完整事件恢复中断会话。
15. 恢复时不重复执行状态不明的写操作。
16. 切换两个 OpenAI-compatible 模型端点。
17. 加载项目 `AGENTS.md`。
18. 加载一个项目级 Skill。
19. 按会话撤销文件修改。
20. 输出完整任务摘要和成本记录。

# 风险分析

## 风险一：通用定位导致功能无限扩张

原因：没有固定业务时，容易把所有 Agent 能力都列为首版需求。

影响：交付延期，评测失去重点。

解决方案：MVP 只实现单 Agent、本地工具、安全权限和可追踪执行；其他能力受阶段门槛控制。

## 风险二：命令风险无法仅靠字符串规则准确判断

原因：Shell 命令可以组合、转义和间接调用。

影响：误放危险命令或频繁误拦截正常命令。

解决方案：字符串分类只作为一层；同时使用工作区限制、权限模式、明确确认、超时和最小环境变量。MVP 不宣称达到操作系统级强隔离。

## 风险三：OpenAI-compatible 协议并不完全一致

原因：不同供应商对流式响应、工具调用和错误结构的实现存在差异。

影响：更换端点后出现兼容问题。

解决方案：Provider 内部做能力声明和兼容层；评测至少覆盖两个端点，供应商差异不得进入 Core。

## 风险四：上下文压缩丢失关键约束

原因：长任务中旧消息和工具结果会超过模型上下文。

影响：Agent 重复工作或违反用户要求。

解决方案：目标、安全限制、用户批准和未完成变更属于不可丢弃状态；只压缩低优先级历史，并用恢复测试验证。

## 风险五：开源许可处理不当

原因：Grok Build 包含 Apache-2.0 一方代码以及保持原许可证的第三方和 vendored 代码。

影响：形成归属不清或缺少声明的代码。

解决方案：默认采用独立实现，仅把公开源码作为架构参考。若后续复制具体实现，必须记录来源、文件、许可证和修改，并保留适用的 LICENSE、NOTICE 和第三方声明。

# 重要决策

1. 项目是通用 Agent Runtime，不绑定垂直任务。
2. 采用 TypeScript 独立实现，不 Fork Grok Build。
3. MVP 只做单 Agent，不做多 Agent。
4. 默认本地运行和本地记录，不上传完整仓库。
5. 安全权限属于 MVP 核心功能，不是后续补丁。
6. CLI 与 Core 分离，为未来 TUI 和其他客户端保留接口。
7. 使用通用任务评测集衡量能力，不使用“什么都能做”作为验收描述。
8. Windows 是首个验收平台，npm 命令使用 `npm.cmd`。
